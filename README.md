# HyperFit Nutrition

بداية تنفيذية لنظام HyperFit للتغذية الذكية وفق مواصفات TDS/SRS والهوية البصرية المرفقة.

## ما تم بناؤه

- تطبيق طبيب عربي RTL متعدد الصفحات باستخدام Next.js وTypeScript.
- تسجيل دخول فعلي بالبريد وكلمة المرور؛ الخادم يحدد دور المستخدم ولا يوجد اختيار للدور في الواجهة.
- كلمات مرور مشفرة بـ PBKDF2، جلسات محددة المدة ومحفوظة كـ hash، وإجبار الحسابات الجديدة على تغيير كلمة المرور الأولية.
- إدارة حسابات للأدمن: إضافة مستخدم أو طبيب أو أدمن، إيقافه، إعادة تفعيله، أو حذفه.
- يستطيع الطبيب والأدمن إنشاء حساب مستخدم كامل، وتظهر بيانات جميع المستخدمين للطرفين مباشرة.
- بوابة مستخدم لعرض بياناته وخطته ووجباته وتسجيل الالتزام، ومساحة طبيب للإدارة والاعتماد، ومساحة أدمن كاملة.
- محرك تغذية حتمي باستخدام `Decimal` لحساب LBM وBMR وTDEE والسعرات والماكروز.
- توزيع أهداف السعرات والماكروز على الوجبات.
- REST API أولي باستخدام FastAPI مع أخطاء منظمة باللغة العربية.
- اختبارات وحدة واختبارات API للحالات المرجعية الأساسية.
- بذرة أولية لقاعدة الأطعمة من القيم الواردة في المواصفات.
- إدارة عملاء فعلية: إضافة وبحث وبدء خطة من ملف العميل.
- دورة إصدارات محكومة: خطة فعالة واحدة مع مسودة مستقلة للإصدار التالي؛ اعتماد المسودة يفعّلها ويستبدل الإصدار السابق مباشرة دون أرشفة.
- تسجيل إكمال الوجبات واحتساب نسبة الالتزام تلقائيًا.
- تسجيل الإكمال محصور بالمستخدم صاحب الخطة، ويظهر مباشرة في تقرير الالتزام لدى الأدمن والطبيب.
- يستطيع المستخدم طلب بديل لوجبته؛ الخادم يطبق حدود نوع الوجبة ويحفظ البديل داخل خطته الفعالة.
- صفحة الإعدادات مخصصة لإدارة الاسم والبريد وكلمة مرور الحساب، مع إعدادات نظام إضافية للأدمن فقط.
- قاعدة أطعمة قابلة للبحث والإضافة.
- تقارير مشتقة من البيانات مع تصدير CSV.
- إعدادات وبيانات تشغيل محفوظة في قاعدة بيانات الخادم بدل `localStorage`.

## تصميم قاعدة البيانات

- `docs/database/SCHEMA.md`: مخطط العلاقات، الأدوار، أنواع الحقول، المعادلات، ونموذج الصلاحيات.
- `docs/database/schema.sql`: تعريف PostgreSQL قابل للتنفيذ ويشمل الجداول والفهارس وRow-Level Security وسجل التدقيق.

التشغيل المحلي يستخدم قاعدة SQLite فعلية في `data/hyperfit.db` لتسهيل التطوير، والنشر يستخدم PostgreSQL عندما يكون متغير `DATABASE_URL` موجودًا. بيانات الجلسات والحسابات والتدقيق محفوظة في جداول مستقلة؛ وحالة الواجهة الحالية محفوظة خادميًا في `application_state` إلى أن تكتمل هجرتها إلى كل جداول PostgreSQL المعيارية.

## التشغيل المحلي

يلزم تشغيل الخادم والواجهة معًا؛ الواجهة لا تقبل دخولًا وهميًا أو كلمة مرور عشوائية.

### الواجهة

```bash
pnpm install
pnpm dev:web
```

تعمل الواجهة على `http://localhost:3000`.

### الخادم الخلفي

```bash
python -m venv .venv
.venv/Scripts/pip install -e "apps/api[dev]"
.venv/Scripts/uvicorn app.main:app --app-dir apps/api --reload
```

يعمل الـ API على `http://localhost:8000`، والتوثيق التفاعلي على `/docs`.

### إنشاء أو إعادة تعيين الأدمن الأساسي

نفّذ الأمر من مجلد `apps/api`، واستبدل كلمة المرور بقيمة قوية لا تُحفظ في المستودع:

```bash
python -m app.bootstrap_admin --email "joudali1910@gmailcom" --name "جود علي" --password "YOUR-STRONG-PASSWORD"
```

سيطلب النظام تغيير كلمة المرور الأولية عند أول دخول. البريد محفوظ كما طلبه المستخدم حرفيًا: `joudali1910@gmailcom`.

### الاختبارات

```bash
.venv/Scripts/pytest apps/api/tests
```

## متطلبات ما قبل النشر العام

النشر يستخدم PostgreSQL دائمًا مع HTTPS وإدارة أسرار، لكنه ليس بعد نظامًا طبيًا معتمدًا. قبل استقبال مستخدمين حقيقيين يجب إضافة rate limiting واسترجاع كلمة المرور والبريد الموثق والنسخ الاحتياطي، واستكمال قواعد الاستبعاد والحساسية الطبية، وإجراء اختبار اختراق ومراجعة امتثال وخصوصية.
